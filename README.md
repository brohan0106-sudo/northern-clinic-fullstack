# Northern Medical Clinic — Clinic Management System

Full-stack artefact for ICT3055 Assessment 3 (Artefact and User Documentation).
Node/Express backend with real authentication, RBAC, and audit logging, serving
a browser frontend. Data persists to a local JSON file — no external database
or account needed to run it.

## Run it

Requires Node.js 18+.

```bash
npm install
npm run seed     # creates data/clinic-data.json with demo accounts + sample records
npm start        # http://localhost:3000
```

`npm run dev` does both steps in one go (handy after wiping `data/` to reset the demo).

## Architecture

```
clinic-fullstack/
  server/
    index.js            Express app: security middleware, route mounting
    config.js            Env config, refuses to boot with the dev JWT secret in production
    store.js              JSON-file persistence with a write queue
    audit.js               Shared audit-log writer
    permissions.js     Single source of truth for role → module ownership
    seed.js               Creates data/clinic-data.json with bcrypt-hashed demo accounts
    middleware/
      auth.js               requireAuth (JWT) / requireRole (RBAC), denials logged
      rateLimiters.js  Brute-force throttling on login + MFA
    routes/                One file per resource — appointments, patients, claims,
                                  insurance, messages, discharge-summaries, register, audit, tests
    utils/
      sanitize.js         Server-side HTML-escaping for all free-text input
      validate.js          Server-side validation (authoritative — not just the UI's)
  public/                   Static frontend (vanilla HTML/CSS/JS), served by Express
  data/
    clinic-data.json    Generated by the seed script — not committed
```

The frontend never talks to a database directly; every read/write goes through
`fetch('/api/...')`, and the server re-checks identity and role on every request.
The sidebar hides modules a role can't use, but that's a convenience — the same
check runs again in `requireRole()` on the server, so calling the API directly
(e.g. from curl or devtools) is blocked identically.

## Security controls implemented (and why each one is real, not simulated)

| Control | Where | What makes it real |
|---|---|---|
| **Authentication + MFA** | `routes/auth.js` | Passwords are bcrypt-hashed at rest; the MFA code is hashed, single-use, and expires after 5 minutes; brute-forcing a code is capped at 5 attempts. |
| **Access control (RBAC)** | `middleware/auth.js`, `permissions.js` | Every API route declares `requireRole(...)`. A denied request gets a real HTTP 403, not a hidden button. |
| **Session management** | `routes/auth.js` | Sessions are JWTs with a 15-minute expiry, delivered as `httpOnly`, `SameSite=Lax` cookies — inaccessible to page JavaScript, so they can't be exfiltrated via a script-injection bug. |
| **Brute-force protection** | `middleware/rateLimiters.js` + per-account lockout in `routes/auth.js` | IP-based rate limiting on `/login` and `/verify-mfa`, plus a 15-minute account lockout after 5 failed passwords. |
| **Input validation & sanitisation** | `utils/validate.js`, `utils/sanitize.js` | Every write endpoint re-validates server-side (required fields, length limits) and HTML-escapes free text before it's stored — the authoritative checks, independent of what the browser already did. |
| **Audit logging** | `audit.js`, `routes/audit.js` | Every sign-in, sign-out, denial, PHI reveal, booking, export and test run is written to a persisted log, visible to staff roles in the UI's live security ticker. |
| **PHI minimisation & re-authentication** | `routes/patients.js` | Patient roster responses return masked MRNs by default; revealing one requires re-submitting the current password, and the reveal itself is logged. |
| **Security headers** | `helmet()` in `server/index.js` | Content-Security-Policy, `X-Frame-Options`, and related headers set on every response. |
| **CSRF mitigation** | `server/index.js` | State-changing requests must carry a custom header a cross-site form can't set, on top of the `SameSite=Lax` cookie. |
| **Data minimisation in API design** | `routes/appointments.js` (`/availability`) | The booking-availability endpoint returns only which time slots are taken, not who booked them — a patient can see what's free without the API leaking other patients' names. |

### Deliberate limitations (documented, not hidden)

- **MFA delivery**: there's no SMS/email provider wired up, so the login response
  returns the demo code directly, clearly labelled `demoCode` and commented in
  `routes/auth.js` as demo-only. A real deployment would deliver this out-of-band
  and never put it in an API response.
- **Reverse-engineering protection**: this is a static Node/Express + vanilla JS
  app — there's no bytecode or compiled binary to obfuscate. The meaningful
  defence is what actually lives server-side (auth, RBAC, validation) versus
  client-side (UI convenience only), which is why every sensitive check in this
  codebase is duplicated on the server even though the browser already did it.
- **Data at rest**: `data/clinic-data.json` is plain JSON on disk, not encrypted.
  Fine for a local demo; a real deployment would use a database with encryption
  at rest and proper access controls, not a flat file.
- **TLS**: the demo runs over plain HTTP on localhost. `secure: true` on the
  session cookie is already wired to switch on automatically when
  `NODE_ENV=production`, which assumes the app sits behind HTTPS in that case.

## System test log

Sign in with any staff account → **System test log** → **Run all tests**. This
calls `GET /api/tests/run`, which executes real assertions against the live
server (`server/routes/tests.js`) — not a hard-coded "always pass" — and writes
each result to the audit log. Covers: authentication, the RBAC policy
invariant, appointment double-booking prevention, patient-registration
duplicate detection, discharge-summary validation, and account lockout.

## Resetting the demo

Delete `data/clinic-data.json` and run `npm run seed` again.
